# Acceptance criteria: Personal AI Daily (spec v1.4.5)

This file is a spec, not a program. Turn each criterion into a check in your own stack and keep the checks in the user's repo (e.g. `verify/`). Run them after every publish, publish the result as `BASE/build_report.json`, and fix whatever fails. Report progress with the **Done definition** at the end.

## Layers
- **R layer (registry-verifiable, blocking).** Needs only public URLs: `BASE` and, for public repos, the GitHub REST API without auth. A registry runs these checks on every admission PR and posts the result as a report. **Registry admission and delisting are decided only by the conditions of §R below** (entry, current liveness, current freshness — the same for admission and the daily recheck); other R results, including past cadence (A7/A7b), never block admission. Your own verification runs all of them, and every R-MUST counts toward your Done definition.
- **S layer (self-attested).** Needs the user's repo, secrets, logs or a re-run. Your verification runs them; a registry cannot, so it reads `build_report.json` and spot-checks with the rubric (§J).

## Notation
- `BASE`: the public site base, e.g. `https://<user>.github.io/<repo>` (no trailing `/`). `REPO`: `profile.site.repo` in one of the SKILL §4.1 forms — `<owner>/<name>` (GitHub), an HTTPS clone URL (another forge), or `local:<path>` (no remote).
- *Repo checks by form* (A1, A5, A8, E2s, E4, E5): **GitHub** — the REST API as written. **Other forge** — the same criteria via `git ls-remote`/an anonymous `git clone` of the URL (A1: it clones without credentials and `BASE/` serves the site; A8: the non-Actions branch). **Local repo** (`local:<path>`, allowed only with `generated_from: fixture`; otherwise A1 FAIL) — the repo is not public: A1 PASSes when `BASE/` serves the site; A5, E2s and E4 run their criteria over every branch of the local repo with `git` (`git ls-tree -r`, `git grep`) and report layer S; A8 uses its non-Actions branch against the local default branch; E5 is N/A ("not a public repo").
- `D`: the issue date under test = the `date` field of `BASE/latest.json`, the local date in `profile.timezone` (SKILL §4.1).
- `GET u`: HTTP GET, redirects followed, **20 s timeout**. URLs under `BASE` get up to 3 attempts with 60–120 s between attempts (deploy lag); **external URLs get exactly one attempt**. Verification requests are not collector fetches (SKILL §2.2): they obey `robots.txt` and send a `User-Agent` naming the verifier.
- `canonical()`, `id`: SKILL §4.4. `tokens()` and `sim(a,b)` (Jaccard): SKILL §2.3. `w()` weighted length: SKILL §2.5.
- **Plain item**: an item without an `entry` field. **Entry item**: an item with one.
- **Raw snapshot**: the run's own saved copy of a page under `raw/<date>/` (SKILL §2.2). Self-verification (S layer, and your own run of R checks) MAY use it when the live page blocks bots (401/403/429 or a challenge page); a registry cannot and then treats that item as not fetchable.
- **Model judgment**: a check marked *judged* (C5b cross-language, C5t, §J) is answered by a **separate judge**: a judge context that is not the writer — a fresh agent or subagent started only for judging, an API model call, or a human — given only the fixed question and the inputs named in the check (never the writer's drafts, notes or rationale). Record each verdict (`item id`, `check`, `verdict`, `judge {kind, id}`, `writer` id, and the quoted passage when the verdict is positive) in `state/judgments/<D>.json` — **private** (SKILL §2.9: it quotes source text). A judged check whose judgment was not made, **or was made by the writer** (`judge.id == writer`, or no separate judge recorded), is SKIP, never PASS. `build_report.json` records `judge {kind, id}` on each judged result.
- **Schema**: validate with **your own vendored copy** of the skill's schema files, selected by `schema_version` (`1.1` → `digest.v1.1.json`, `1.2` → `digest.v1.2.json`, `1.3` → `digest.v1.3.json`; `1.0` is history only) and, for `index.json`, `index.v1.json`. Never validate with a schema fetched from the site under test. Use JSON Schema 2020-12 **with format assertion enabled** (otherwise `2026-02-30` passes). Registries accept new submissions at ≥ 1.1; earlier issues read for D2 are not schema-validated.
- **Canonical hash** of a schema file: SKILL §4.3.

**Statuses.** Every check outputs `{id, layer: R|S, level: MUST|SHOULD, status: PASS|FAIL|WARN|SKIP|N/A, observed, expected, fix}`.
- `PASS` / `FAIL`: the criterion holds / does not hold.
- `WARN`: a SHOULD that does not hold. A MUST never ends at WARN.
- `SKIP`: the check could not run this time (network error, rate limit). It is never counted as PASS, and a MUST at SKIP blocks "done".
- `N/A`: the check does not apply: its module is disabled (e.g. the private brief), its population is empty (no entry items for D0s, no follow-ups for D3, no earlier issue for D2), or a first-run rule below says so. `observed` states why (e.g. `0 entry items`). N/A counts as neither PASS nor FAIL.

The run exits non-zero on any MUST at FAIL. Checks never print secret values or the forbidden-word list; print counts only.

**Report.** `build_report.json` = `{for_date, generated_at, schema_version, counts, results[]}`, where `counts` has exactly the keys `PASS`, `FAIL`, `WARN`, `SKIP`, `N/A` (integers, zeros included) over all results of that run, and `results[]` = `{id, layer, level, status}` per check, plus `judge {kind, id}` on judged results (C5b when it judged cross-language items, C5t, J). The §J rubric is reported as result **`J`** (layer S, level MUST): PASS when all sampled items pass, FAIL otherwise, SKIP when no separate judge scored it; per-item scores go to the private `state/judgments/<D>.json`. B11 is part of the run that produced the report (it checked the *previous* report), so it appears in `results` like any other check.

**First run** (no earlier issue in `index.json`): A7 evaluates the one issue that exists; A7b is N/A; B11 is N/A (no earlier report can exist); D2/D2s are N/A; every other check runs normally.

**Fixture / test runs** (`generated_from: fixture`): A7s checks that the daily task is *declared* (the artifact exists and is well-formed), not that it has run; everything else is unchanged.

**C5b procedure:**
1. *Candidates:* items of D with a non-empty `summary`, in ascending `id` order.
2. *Source text:* `GET canonical_url` (20 s, one attempt; self-verification may use the raw snapshot). The item is *not fetchable* unless the status is 200, the type is `text/html` or `text/plain`, and its readable text has ≥ 200 characters. Decoding and readable text: exactly SKILL §2.5 (*Readable text and script class*): HTTP charset → `<meta>` charset → BOM → detection. x.com and other login-walled pages are not fetchable unless a raw snapshot exists.
3. *Script class:* the SKILL §2.5 script-class function (first 6,000 characters, URLs/e-mails/hex- and base64-like tokens removed, CJK if ≥ 30% of the remaining letters are in the weight-1 ranges), applied to the summary and to the source text — the same function the pre-publish gate (C5g) uses.
4. *Same class → deterministic:* casefold both texts and collapse whitespace; compute the longest common substring in characters. Copy = LCS ≥ 40 characters (Latin) or ≥ 20 (CJK).
5. *Different class → judged (cross-language):* give the judge the summary and the first 6,000 characters of the readable source text, and ask exactly: "Is SUMMARY a translation or a close paraphrase of one contiguous passage of SOURCE — the same facts in the same order, sentence by sentence? Answer yes or no; if yes, quote the passage." Copy = yes. A language difference never makes an item skippable. The judge is a separate judge (Notation).
6. *Sampling:* walk the candidates until 5 items have been **evaluated** (step 4 or 5) or 15 have been tried. At least 3 must be evaluated. **In addition, every item that has a current separate-judge C5b verdict** (from the pre-publish copy gate, SKILL §2.5) is part of the audit, whatever its position in `id` order; a verdict is current only if the summary it judged equals the item's current summary.
7. *Status:* FAIL if any evaluated item is a copy; PASS if ≥ 3 items were evaluated and none was; SKIP if a cross-language item could not be judged (no model available); **N/A only if fewer than 3 candidates had fetchable source text** (observed: counts). Items with `summary == ""` are never copied text and are not candidates.

## R. Registry conditions (run by a registry, SKILL §5; not part of a digest's own `build_report.json`)
The same three conditions decide admission (PR) and the daily recheck. Nothing else blocks.

| ID | Criterion | How |
|---|---|---|
| G1 entry | `curators/<name>.json` (JSON, not YAML) validates against the registry's vendored `curator-entry.v1.json` (format on); `name` = file name; new entry: `name` and `canonical(url)` not used by another entry (listed or delisted); existing entry (rename, move, restore, any edit): the PR opener's **GitHub numeric user id** = `author_id`; `canonical(url)` = `canonical(latest.json curator.url)` = `canonical(BASE)` (B13); `opml` only if `index.json` has `sources_opml`; the PR does not set or edit `author_id`/`joined_at`/`delist_history`; `restore` only when the entry is delisted; every closed `delist_history` interval has `to` ≥ `from` (compared as instants); the PR deletes no file under `curators/` (a deletion is always rejected); `latest.json.generated_from` ≠ `fixture` | parse; GitHub PR metadata (`user.id`) |
| G2 liveness (now) | B3 (issue schema), B4, B5 (incl. index schema) and B6 PASS at check time, with the registry's own vendored schemas | GET |
| G3 freshness (now) | `max(index.json.dates[].published_at)` ≥ check time − 14 days (instants, UTC) | read index.json |

- **Admission:** G1, G2 and G3 PASS. All other R checks are reported on the PR, non-blocking.
- **Delist `down`:** G2 FAIL on 3 consecutive completed daily checks (a day without a completed registry run, or a void run whose registry reachability probe failed, neither counts nor resets). **Delist `stale`:** G3 FAIL. Delisting appends `{from, to: null, reason}` to `delist_history` and keeps the file.
- **Restore:** a PR from the same `author_id` adding only `"restore": true`; G1–G3 PASS; at merge the registry closes the open interval (`to` = merge time) and removes `restore`. `delist_history` is never shortened; `name`, `author_id` and `joined_at` are kept.
- The co-selected leaderboard (SKILL §5.5) is experimental and has no check here.

## J. Judgment rubric (result `J`, S layer, MUST; scored by a separate judge — a human or a judge context that is not the writer; a registry spot-checks 5 items)

**Sampling:** walk all items of issue D in ascending `id` order and take an item only if its section has not been sampled yet, until 5 are taken. **If fewer than 5 items were taken** (e.g. fewer than 5 non-empty sections), walk again from the smallest `id` and fill up with items not yet taken until 5 are taken (or the issue has no more items).
Score each item 0/1/2 on five criteria. **Pass: total ≥ 7/10 and no criterion at 0.** An item with `summary == ""` scores 2 on criterion 1 (nothing was copied) and is judged on its title and `why`. Criterion 1 for a title: a headline per the SKILL §2.5 title rule is not "copied".

| # | criterion | 2 | 1 | 0 |
|---|---|---|---|---|
| 1 | own words | rewritten, adds context or significance | close to the source's word order (a translation) | copied, or a translation of a whole post/paragraph |
| 2 | why has a view | states impact on the reader or a judgment | generic ("worth watching") | empty, or repeats the summary |
| 3 | facts traceable | every number/name in the summary is on `canonical_url` (or, when that page blocks bots, in the run's raw snapshot of it or of the other fetched sources of the event) | one fact not found | something invented |
| 4 | follow is a delta | only the change (non-follow items score 2) | mixes in old content | no new fact |
| 5 | link is the origin | vendor, repo, paper or original post | secondary media | aggregator or digest page |

Counterexamples (MUST fail):
- An x item whose title and summary are both the Chinese translation of the full tweet and whose `why` is empty (e.g. a post by addyosmani, `x.com/i/status/2108969481271939340`): criterion 1 = 0, criterion 2 = 0.
- `title == summary` on a quoted book passage tweet (mattpocockuk, `…/status/2108985674657362080`): fails C5 mechanically and criterion 1.
- A summary that is the first sentence of the source article: fails C5b and criterion 1.
- A Chinese summary that is a sentence-by-sentence translation of an English source paragraph: fails C5b (judged) and criterion 1.
- A summary of a title-only feed entry that restates the headline: must be `""` instead (SKILL §2.5 headline-only items).
- A follow-up "后续｜X 继续发酵": criterion 4 = 0.
- `canonical_url: https://example.com/`: 200 but not a source — fails C4.
- `interests` copied verbatim from the SKILL example — fails A2.

Counterexample (a "fix" that still fails): the same Addy Osmani tweet with summary "AI 辅助工程已是默认；优势来自多年与 agent 的实际磨合，并且会复利" — each clause is one sentence of the tweet translated in the tweet's order, so it is a sentence-by-sentence translation: criterion 1 = 0 (and C5b yes when judged).

Passing examples:
- Short post (same tweet, fixed): title `@addyosmani: 与 agent 长期磨合` (SKILL §2.5 social-post title); summary `""`, because a one-paragraph post can only be translated, not synthesized; why "把“会用 agent”从技能变成积累：团队要沉淀这些人的用法，而不只是买工具" (a judgment for the reader, not a restatement). → criterion 1 = 2 (empty summary), 2/2/2/2/2.
- Long source (a release-notes entry that lowers a cache-read price and, in the same entry, ships other changes): summary "长系统提示、反复注入记忆这类重度依赖缓存的用法直接降本——缓存读取从基础输入价的 0.1 倍降到 0.05 倍，其余价格未动". It leads with what the change means for the reader, keeps only the facts that support that point, and combines the price with "other prices unchanged" from a later sentence instead of walking the entry in order. → 2/2/2/2/2.
- Unfetchable source (page blocks bots, nothing stored): summary `""` plus a why; a non-empty summary on an item whose stored source is empty, near-empty or unrelated to the summary is `no-source` and blocks publishing (criterion 3 cannot be scored).

## Done definition
- **Provisionally done** (reachable in the first session): the first issue is live, and every MUST row (R and S) is PASS or N/A under the first-run rules — with C5g at PASS, C5b at PASS (or N/A only because fewer than 3 sources were fetchable, never because of language), and result `J` at PASS, all judged parts by a separate judge (a self-judged result is SKIP and blocks). Tell the user "provisionally done", give the URLs below, and say when the scheduled runs will happen.
- **Done**: additionally, two runs triggered by the schedule (not by hand), on two consecutive scheduled days, each ended with every MUST PASS or N/A, and A8 reports `success` for the second. Then report the URLs again as done.
- **Test done**: a digest with `generated_from: fixture` can reach only this state (the same criteria as provisionally done, with A7s checking only that the daily task is declared); it is not eligible for a registry.

URLs to report: `BASE/`, `BASE/latest.md`, `BASE/llms.txt`, `BASE/SKILL.md`, `BASE/feed.xml`, `BASE/index.json`, and `BASE/sources.opml` only when `site.publish_sources: true`.
