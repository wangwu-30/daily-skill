# Personal AI Daily: a skill whitepaper (spec v1.4.5)

## 0. The idea
For twenty years, platforms decided what information reached you. Feeds, trending lists and recommendation engines were tuned to their goals, not yours. Agents change the economics. Your own AI can now read the sources, follow the people you trust, drop repeats, rank against **your** interests, and publish a clean daily brief. Other people's agents can read that brief and use it as a source.

So distribution comes back to individuals and the people they trust: a network of personal curators, each publishing in an open format, replaces the platform as gatekeeper.

**This skill is the open source; the code is generated by your AI.** It ships no programs and no template repo. It ships:
- `SKILL.md`: this whitepaper. It covers the goal, the closed loop, design principles, config and output schemas, the canonical-URL/id algorithm, the privacy and state policy, the failure policy, and the registry.
- `ACCEPTANCE.md`: declarative, machine-checkable criteria in two layers. The **R layer** is what anyone (e.g. a registry) can verify from public URLs. The **S layer** is self-attested inside the user's repo. Your agent writes its own verification from them, runs it, and fixes what fails.
- `schema/`: the public output contracts (JSON Schema 2020-12): `digest.v1.3.json` (current), `digest.v1.2.json`, `digest.v1.1.json` and `digest.v1.json` (older versions, kept for history), `index.v1.json` (the site index, §2.6), and `curator-entry.v1.json` (a registry's `curators/<name>.json`, §5.1).

You are an agent. Read these documents, then build the system in the user's GitHub account in whatever stack you choose. You are done per the Done definition in `ACCEPTANCE.md` (provisionally after the first run, fully after two scheduled runs). **Done needs a separate judge** for the judged checks (§2.5): a subagent, a second agent, an API model or a human — anything but the context that wrote the prose. Without one, result `J` stays SKIP (so Done, even test done, is not reachable), and every summary of a source in another script than the digest must be `""` (the cross-language copy question cannot be answered).

**The human does at most two things:**
1. `gh auth login`.
2. Optional: add an LLM API key as a repo secret, so the scheduled workflow can write prose by itself (`llm.mode: api`). Without one, prose is written by the user's own agent (`llm.mode: agent`, §2.5). "Zero-key" means no *extra* API key, never "no model": the agent running this skill is a model.

You do everything else and verify it yourself: config, repo, workflow, hosting, the first run, the checks, and the fixes.

Normative words: MUST / SHOULD / MAY as in RFC 2119. Every threshold in this file is exact, not "about".

## 1. Goal
Each day, publish a short digest written for one reader:
- Humans read it as a static page.
- Agents and other digests read the same content through stable endpoints: `llms.txt`, Markdown, JSON (`digest.v1.3`), Atom, `SKILL.md`, `index.json` (and `sources.opml` only if the curator opts in, §2.6).
- Each story appears once. If it returns, it is labelled a **follow-up** and states only what changed.
- Every summary is in the curator's own words; nothing is copied from the source (§2.5).
- Raw fetched text and the store never appear in public output **or in any public git branch** (§2.9).
- The default deliverable is public only. A personal **private brief** is an optional module, off by default (§2.5).

## 2. The closed loop
```
interview ─► config/profile.yaml + config/sources.yaml
   ▲                                │
   │                                ▼
feedback ◄─ publish ◄─ render ◄─ gates ◄─ edit ◄─ rank ◄─ cluster/dedupe ◄─ store ◄─ collect ◄─ (registry peers)
   │           └─► agent entry points: llms.txt · index.md · data.json · latest.* · index.json · feed.xml · SKILL.md · (sources.opml, opt-in)
   └─ "less X", "more Y", "this was a repeat" → profile.yaml + state/feedback.json
```

### 2.1 Interview → config
Ask 6–10 short questions. First read any public material the user points you to (site, GitHub stars, posts) and infer what you can.

Cover:
- Topics to boost, ranked (≥ 3), with the words that identify each (→ `interests.*.keywords`), and topics to mute (→ `mute`, hard exclude) or to see less of (→ `negative`, down-rank).
- 5–20 **trusted people** and the products whose changelogs they follow.
- Language and **timezone** (IANA name). There is no fixed publish time: each issue goes out as soon as it is ready.
- Sections (§4.1 section set), section titles, and the empty-section placeholder text.
- Where the site lives (`site.base`, `site.repo`) and the curator name shown to readers (`site.curator_name`).
- Whether any private words must never appear publicly (project names, client names). If yes they go into the repo secret `FORBIDDEN_WORDS` (`privacy.forbidden_words: secret`); if the user says there are none, record `privacy.forbidden_words: none` (E1 then checks the default leak list only).
- Whether they want the optional **private brief** (default: no) and, if yes, the private channel to receive it on (their agent chat, email or IM).
- **Source list (optional).** Ask whether to publish the source list as `sources.opml` (default **no**: the subscription list is part of the curator's value and stays private; per-item source links are always shown). Record the answer as `site.publish_sources` (§2.6).
- **Separate judge.** Ask who can judge the judged checks (§2.5): a subagent or second agent of their platform, an API model (key as a repo secret), or the user themself. State the consequence plainly: "Without a separate judge the digest cannot reach Done, and summaries of sources in other languages are left empty." Record the answer as `llm.judge` (§4.1).
- **Profile visibility.** Tell the user plainly: "In a public repo, `config/profile.yaml` (interests, mutes, trusted people) is public." Offer the private options (§2.9) and record the choice as `profile_visibility`.

Then:
- Write `config/profile.yaml` (with `generated_from: interview`) and `config/sources.yaml`. Do not copy the example values of §4.1; they are illustrations.
- Save the questions and answers to `state/interview.md` (≥ 6 Q&A pairs, lines starting `Q:` and `A:`) in the same place the profile lives (private if the profile is private).
- Show a 10-line summary, apply their edits, and stop asking.

**Non-interactive / test runs.** When no human is available (CI tests, cold-start trials), use a written persona, record the simulated Q&A in `state/interview.md` marked `simulated: true`, and set `generated_from: fixture`. A fixture-profile digest is a test: it MUST NOT be submitted to a registry and can reach only "test done" (ACCEPTANCE, Done definition).

### 2.2 Collect → store
- Each source has an `id`, a `type`, a `lane` (`followed` = asked for, `discover` = broad recall), a `topic` and `enabled` (§4.2).
- Save every raw fetch under `raw/<date>/` so you can replay a day offline. **`raw/` is private state** (§2.9): never commit it to a public branch.
- Upsert into a single store (SQLite is enough). The store key of a raw item is `canonical(url)` + (`"#" + entry` when the item is one entry of a multi-entry page, §4.4), or a content hash when there is no URL. Re-running collect on the same day **replays `raw/<date>/`** (no network) and MUST add zero rows.
- **Fetch ladder:**
  1. A machine-friendly variant: `.md`, RSS/Atom, JSON API, releases API.
  2. A reader proxy (e.g. `https://r.jina.ai/<url>`). The proxy is a fetch method only: its URL never appears in output.
  3. A headless browser for JS-rendered pages.
- **Access rules (all rungs, including the proxy and the browser):**
  - Use only legitimate public access: no login or paywall bypass, no paid endpoints the user didn't approve, no personal timelines unless asked.
  - Obey the target site's `robots.txt` and ToS.
  - At most **1 scheduled fetch per source per day**.
  - **robots.txt** (RFC 9309): read it once per host per run before the first request. 2xx → obey it; 4xx → no restrictions; timeout, network error or 5xx → **do not fetch that host in this run**: skip its sources, log them as failed with reason `robots-unreachable`, and try again in the next day's run.
  - **Redirects.** robots.txt applies per host **after redirects**: before following a redirect to another host, read that host's robots.txt (same rules) and follow only if it allows the target path; otherwise stop and log `robots-disallowed` with the redirect target. The fetch log (private, `raw/<date>/fetch_log.jsonl`) records for every request: source id, requested URL, **final URL** (after redirects), status, bytes, time, and the robots verdict for each host on the chain.
  - **Robots-blocked sources are disabled.** A source whose URL (or its final URL) is disallowed for your user agent is not a source: set `enabled: false` with `x-disabled: robots` in `sources.yaml`, tell the user once (at the interview when you can see it then, else in the next brief/chat), and do not count it toward the 3-day failure rule. Known cases: YouTube channel feeds (`youtube.com/feeds/videos.xml`), `export.arxiv.org` (the arXiv API). There is no free compliant route for YouTube channels; offer the channel owner's own blog/newsletter feed instead.
- **What counts as one fetch.** A *source* is one `sources.yaml` entry, or one repo / product inside an entry that lists several. One *fetch* is everything the collector requests for that source in one run: pagination, every query of a multi-query `json_api` entry, every rung of the ladder, and following links from a feed, changelog or index page to its own entry/article pages (at most 10 such pages per source per run). **Which entries get a page:** only entries that are candidates (in the fetch window, not muted, not already in the ledger as a non-follow-up), newest first by item date (ties: feed order), until 10 pages are fetched; prefer entries whose feed description has < 200 readable characters by moving them ahead of those with a longer description. An entry without a fetched page uses its feed description as its stored source text (the copy gate checks against that, and a description too short to be a source makes the item headline-only, §2.5). `robots.txt` requests do not count. A run that replays `raw/` makes no fetch. Development and debug runs that hit the network **do** count; replay `raw/` instead when iterating.
- **Verification requests are not fetches.** Requests made by the checks (ACCEPTANCE C3, C5b, D0s and the ACCEPTANCE §J rubric) do not count toward the per-source limit; they still obey `robots.txt` and send their own `User-Agent` that names the verifier.
- **The ladder runs only inside the source's single daily fetch.** All rungs are tried in the same run; once the run ends, the next attempt is the next day's run (or a replay of `raw/`).
- **What counts as a failed fetch.** A fetch (or rung) fails when the status is not 2xx-with-body (e.g. 202 with an empty body, 4xx, 5xx, timeout), **or** the body is empty, **or** the content does not match the source's type: a `feed` that does not parse as RSS/Atom (an HTML page, a JS/bot challenge), a `json_api` that does not parse as JSON, a page whose readable text is < 200 characters. A 200 that is not the expected content is a **failure**, never "0 new items". A failed rung climbs the ladder; a source whose rungs all fail is logged as failed with its id and reason.
- **Fix-now policy:** when a source fails, log it with its source id, skip it, and still ship.
  - Climb the ladder in the same run, and write the method that worked into `sources.yaml` (`method`) or state.
  - If it fails 3 days running, tell the user and propose a fix.
- **Secret-bearing URLs.** A source URL whose query matches `(?i)[?&](token|key|apikey|api_key|access_token)=[^&]{16,}` (private RSS, keyed APIs) MUST NOT be written to any tracked file or to `sources.opml`. Put the URL in a repo secret, reference it as `url_env: <SECRET_NAME>`, and mark the source `opml: false`.

**Fetch window.** Per issue, `fetch_window.start` = the previous issue's `fetch_window.end` (first issue: `end − 24 h`) and `fetch_window.end` = the time the last fetch of this run finished. A source MAY declare `lookback_hours` (default 0); its candidates are items whose *item date* is ≥ `start − lookback_hours`. An item date that is a **date only** is in the window when that date ≥ the local date (in `profile.timezone`) of `start − lookback_hours`. Novelty is still enforced by the ledger (§2.3), so a longer lookback never causes repeats.

**Papers.** Use `https://rss.arxiv.org/rss/<cat>` as `type: feed, kind: paper` (html: `https://arxiv.org/list/<cat>/new`), and/or the Hugging Face daily papers page or its JSON (`type: hf_papers`). Do **not** use the arXiv API (`export.arxiv.org`): its robots.txt disallows all agents. arXiv RSS is valid but **empty** on days without an announcement (weekends, holidays): that is "0 new items", not a failure; the next announcement brings them (the ledger prevents repeats). If you want papers on those days, keep the last announcement's unpublished items in private state and rank them in the next run, or rely on `hf_papers`. An `hf_papers` item's `canonical_url` is `https://arxiv.org/abs/<id>` (the paper's publisher); the HF page is a discovery route only — it is not a publisher, not added to `sources`, and does not count toward `source_count`.

**URL templates.** A source `url` MAY contain `{date}` (= the issue date `YYYY-MM-DD`) and `{since}` (= the local date of `fetch_window.start − 14 days`), e.g. GitHub search `…/search/repositories?q=topic:llm+created:>{since}&sort=stars`. No other placeholders.

**Item date by kind** (used for the window, for item `published_at`, and for "newest"):

| kind | item date |
|---|---|
| feed / article | the entry's `published` (else `updated`) |
| GitHub release | the release's `published_at` |
| repo from trending | the day it was observed trending (fetch date) |
| repo from search | `created_at`. **This kind does not use the fetch-window test:** a repo is a candidate when `created_at ≥ start − 14 days`; older repos only via trending or a followed source; novelty is enforced by the ledger |
| changelog entry | the date shown with the entry; an undated entry gets the date it was first stored (`raw_items.fetched_at`) |
| paper | the announcement date when the source states it (arXiv RSS/listing), else the date the source gives for the paper (e.g. the HF papers `publishedAt`) |
| video | the publication date the page or feed states |
| social post | the post time |
| registry peer item | the peer item's `published_at`, else the peer issue `date` |

### 2.3 Cluster / dedupe
Attach each item to an **event**: one real-world development. Each event has a **key**:

| key format | used for |
|---|---|
| `release:<owner>/<repo>@<tag>` | a GitHub release (owner/repo lowercased, tag as shown) |
| `repo:<owner>/<repo>` | a repository itself (lowercased) |
| `entry:<canonical>@<entry>` | one entry of a multi-entry page (§4.4) |
| `url:<canonical>` | everything else (`canonical()` of §4.4) |

Keys match `^[A-Za-z0-9][A-Za-z0-9._:/@+-]{0,127}$` after replacing characters outside that set with `-`; if longer than 128 characters use `<type>:` (the key's own prefix: `release`, `repo`, `entry` or `url`) + the first 16 hex of SHA-256 of the canonical (+ `#` + entry for entry keys), so different entries of one long URL never collide.

The first matching rule wins:
1. Same key (same `canonical(url)`, same entry, same release, or same repo).
2. Alias: an aggregator item carries the original URL, or a post quotes one → use the original's key.
   - 2b. **Release ↔ changelog entry.** A changelog entry of followed product P joins the event `release:<owner>/<repo>@<tag>` when `sources.yaml` maps P to that repo (`products.<P>.repo: owner/repo`) and the entry's version label equals the tag, ignoring a leading `v`/`V` and case ("Version 3.15.0" ↔ `3.15.0`). The merged item is one item (link: the release tag page; the changelog entry goes into `sources`).
3. A release never joins its repo's event, and a repo never joins a release's event: they are different developments. A repo may publish many releases; keep **at most 1 release per repo per issue** (the newest by item date) and say "and N earlier builds" in the summary when several fall in the window.
4. Title similarity **≥ 0.6** against events whose `last_seen` is within the last **7 days**. Similarity = Jaccard over tokens, where tokens = the set of lowercased Latin words matching `[a-z0-9][a-z0-9.\-]+` ∪ the set of CJK character bigrams (consecutive pairs after deleting every character outside U+3040–U+30FF (hiragana, katakana), U+4E00–U+9FFF (Han) and U+AC00–U+D7AF (Hangul), so Japanese and Korean titles have tokens too). Two empty token sets have similarity 0. Rule 4 **never** merges two items (a) from the same source id, or (b) whose token sets differ in any token that contains a digit (versions, numbers: "Chrome 153-154" vs "Chrome 155-156") — ignoring tokens that are a 4-digit year (`19xx`/`20xx`) or a date (`2026-10-05`, `10-05`, `oct-5`), which say when, not what.
5. Optional embedding similarity, only when embeddings are enabled (cosine ≥ 0.85), with the same two exclusions.
6. Otherwise, a new event.

**`signals.source_count`** = the number of distinct *publishers* among the event's merged items. Publisher = the `canonical()` host, except on shared platforms (`x.com`, `github.com`, `huggingface.co`, `bsky.app`, `medium.com`, `substack.com`, `youtube.com`), where it is host + first path segment (the account). Each registry peer counts as one more publisher. Three entries from one page are 1 publisher. It is ≥ 1.

**Publications ledger** (the one definition; §2.9 and §4.5 refer here). One row per published item:

| column | meaning |
|---|---|
| `event_id` | internal event id |
| `key` | the event key above |
| `canonical_url` | as published |
| `entry` | as published, or null |
| `date` | issue date |
| `section` | section id |
| `as_followup` | boolean |
| `title` | our published title |

It holds no article text. Two gates **fail the build**:
- An event may appear at most once per issue, in its highest-priority section (priority = order of `profile.sections`).
- *Previously published* means a ledger row with `date < D`. When issue D is rebuilt on the same day, its own rows (`date == D`) are deleted and written again from the new build; they never count as history for D.
- A previously published event may appear only as a follow-up, which states only the delta: a new version, new numbers, or a new official statement. Counterexample that MUST fail: "后续｜X 继续发酵" ("X keeps trending") — no new fact.

### 2.4 Rank
- **Two recall lanes.**
  - `followed`: items from `lane: followed` sources, from followed products, and items posted, starred, released or quoted by trusted people.
  - `discover`: everything else, plus items similar to `profile.interest_text` when embeddings are on.
  - `recall_mix` is a **target** share of followed vs discover items over the whole issue excluding `top3`. It is not enforced (the enforced rule is `min_followed_share`); a generator MAY report the achieved followed share as the top-level scalar `x-recall-followed` (0–1) in `data.json`.
- **Relevance.** `interests` maps a name to either a weight or `{weight, keywords}`; the bare form means `keywords: [name]`. `negative` is the same shape. Keyword matching runs over the item's source title + source description (+ repo topics / release name), **case-insensitively**:
  - A keyword that contains a CJK character (SKILL §2.5 weight-1 ranges) matches as a **substring**.
  - Any other keyword matches as a **whole word**: the character before the match and the character after it are each the start/end of the text or not an ASCII letter or digit (`[A-Za-z0-9]`). Inner characters match literally (`llama.cpp`, `multi-agent`). So `crypto` does not match "cryptography", `DeFi` does not match "define", `quant` does not match "quantitative".
  - A keyword ending in `*` is an explicit **prefix**: `quant*` matches "quant", "quants", "quantitative" (the left side is still a word boundary).
  - `m_i = 1` if any keyword of interest *i* matches, else 0.
  - **`negative` only down-ranks; `mute` excludes.** `profile.mute` is a list of keywords (same matching rules); an item matching any of them is **dropped in every lane**, followed and trusted included, before ranking. Topics the user asks to mute at the interview go to `mute`; topics to see less of go to `negative`.
  - `relevance = clamp((Σ_i w_i·m_i − Σ_j n_j·m_j) / max_i w_i + trust_bonus, 0, 1)`, where `trust_bonus = 0.2` if a trusted person posted, starred, released or quoted the item, else 0.
- **Multi-score.** Each component is normalized to [0,1]; `score = Σ weight_k · component_k` with the weights from config (they sum to 1).
  - `novelty`: new event = 1; follow-up with a delta = 0.35; follow-up without a delta = dropped.
  - `signal = max_k min(1, log10(1 + x_k) / log10(1 + cap_k))` over `stars_delta` (cap 10000), `likes` (cap 5000), `upvotes` (cap 500), `source_count − 1` (cap 5). Missing values count as 0.
  - `actionability` by the item's **kind** (below): `release`, `changelog` 1.0; `repo`, `paper` with a code link 0.8; `paper` 0.6; `news`, `article` 0.4; `link`, `discussion`, `social`, `video` 0.2.
- **Item kind** (deterministic): from the source type — `github_releases` → `release`; `changelog` → `changelog`; `github_trending` → `repo`; `hf_papers` → `paper`; `social` → `social`; `registry` → the peer item's kind if it states one (`x-kind`), else `article`; `feed` and `json_api` → the source's `kind` field (one of `news`, `article`, `paper`, `repo`, `release`, `link`, `discussion`, `video`; required for these two types). A `json_api` returning repositories uses `kind: repo`; HN/Reddit listings use `kind: discussion` (their linked article, once resolved, keeps that kind for ranking).
- **`stars_delta`** = today's `stars_total` minus the total in the previous daily snapshot (private state), with `stars_delta_period: "day"`; it is `null` (absent) when there is no earlier snapshot, so on day 1 repos rank by the other components. GitHub's trending page has no API: fetch `https://github.com/trending` at most once a day and only if its `robots.txt` allows it for your user agent; otherwise use the search API (`created:>…` sorted by stars) plus snapshots.
- **Social-proof gate** for non-followed items: they need `source_count ≥ min_sources`, or `stars_delta ≥ min_stars_delta`, or `likes ≥ min_likes`, or `upvotes ≥ min_upvotes`, or `relevance ≥ min_relevance` (default 0.6).
- **Post-rank rules**, applied per section in this order:
  1. Negative-feedback downweight: `score × (1 − negative_feedback_penalty)` for events/sources listed in `state/feedback.json`.
  2. `min_followed_share`: in each section except `top3`, at least `ceil(min_followed_share × n)` of its `n` items are followed-lane items, swapping in the best remaining followed candidates **that qualify for that section**; if there are not enough, keep what exists (best effort) and log the shortfall.
  3. `max_same_source_run`: within a section, no more than this many consecutive items from one source id; move the next item from another source up. If no item from another source remains, **drop the rest of that run** (best effort) and log it.
- **Issue shape** (`profile.issue`, §4.1):
  - `top3` holds the 3 highest-scoring items of the day, **at most 1 per publisher** (§2.3 publisher); with fewer than 3 eligible items it holds what exists (0 → placeholder). Items in `top3` do not repeat in other sections.
  - A `col-<slug>` column takes the items that match its interest (`profile.columns.<id>.interest`), up to `max_items_per_column`.
  - Every other section takes the items that qualify for it (**section qualification** below), in score order, up to `max_items_per_section`; the whole issue holds at most `max_items_total`.
  - **Section qualification** (deterministic, no judgment): an item qualifies for a section when
    1. its source declares `section: <id>` in `sources.yaml` — then for that section only (plus `top3` and columns); else
    2. by the standard table in §4.1 (`cl`: kinds `changelog` from `followed_products` **and** `release` from `lane: followed` `github_releases` sources; `gh`: kind `repo`, and `release` from `lane: discover`; `papers`: kind `paper`; `x`: kind `social`; `biz`: kind `news`; `eng`: kinds `article`, `link`, `discussion`, `video`; `infra`: never by default — only via `section_rules`); else
    3. a custom or overridden section declares `profile.section_rules.<id>: {kinds: [...], interests: [...], sources: [...]}` — an item qualifies when its kind is in `kinds` (if given) **and** it matches one of `interests` (if given) **and** its source id is in `sources` (if given). A custom section without `section_rules` takes only items from sources that declare `section: <id>` (rule 1); with neither it takes no items (it shows the placeholder).
  - An event belongs to the highest-priority section it qualifies for; priority = order of `profile.sections`.
  - In HTML, items after the first `fold_after` of a section are folded under "More".
- **Trusted people without paid X access.** The free routes are their GitHub activity (stars, releases of their repos), their blogs' RSS, and public Bluesky (`https://bsky.app/profile/<handle>/rss`) or Mastodon (`https://<instance>/@<user>.rss`) feeds. YouTube channel feeds are robots-disallowed (§2.2), so a trusted person who publishes only on YouTube has no free compliant route — say so at the interview. If none of the trusted people publish anywhere free, the `x` section stays empty (placeholder) or is removed from `profile.sections` with the user's consent.

### 2.5 Edit
Every public item gets a title (the title rule below), a summary, tags and a `why` line. Summary and `why` are written by a model in the curator's own words from fetched facts only, with exact URLs. Merge multi-source events into one item tagged "N sources" (N = `source_count`).

**Title rule (one rule, every mode).** The title is the source's own headline, **translated into `profile.language` when it is in another language**, and otherwise unchanged: never rewritten into a summary, never extended with facts from other sources, never a "framing" of our own. Light normalization is allowed: drop the site name and trailing boilerplate, and prefix `后续｜`/`Follow-up: ` on follow-ups. Where a kind has no headline:
- release: `<product or repo name> <tag>` (`llama.cpp b6712`);
- changelog entry: `<product>: <the entry's heading>`, or `<product> <entry date>` when the entry has no heading of its own;
- repo: `<owner>/<repo>`, optionally `: <its GitHub description, translated>` cut to weighted length 60;
- paper: the paper's title (translated when needed);
- social post: never the post text — `@<handle>: <subject>`, where the subject names what the post is about in ≤ 6 words (in `none` mode: `@<handle> on <matched keyword>`); weighted length ≤ 60.

**Facts for the summary.** The summary may use only facts the pipeline fetched for that item: the source page, the feed entry's description, or the article page that a feed entry links to (fetched as part of the source's daily fetch, §2.2, at most 10 per source per run). **Headline-only items:** if all that was fetched is the headline (title-only feeds, a blocked article page), the item gets title + `why` only, with `summary: ""` — never a summary that restates or translates the headline. The agent MAY fetch the article page to get facts; then a normal summary is required. **Short sources:** a single short social post, a repo whose only text is its one-line description, or a quoted passage is treated the same way — title + `why`, `summary: ""` — because any summary of it would be a translation. A summary is written only when the fetched text has enough facts to synthesize: lead with what it means for the reader, combine facts from different parts of the source, and never walk one passage in order.

**Who writes the prose** (`profile.llm.mode`):
- `api` — the scheduled workflow calls an LLM with the key in the secret named by `llm.api_key_env`.
- `agent` (the default; "zero-key") — the user's own agent writes the prose. The agent running this skill is a model, so no extra key is needed. Run the daily job as the agent's own scheduled task (or have it pick up the workflow's candidate file, write `edits/<date>.json`, and trigger `workflow_dispatch`); the gates, render and deploy stay deterministic code. **The candidate file and every other editor input carry fetched source text: they live under `raw/<date>/` (e.g. `raw/<date>/candidates.json`) and are private (§2.9).** `edits/<date>.json` holds only our own prose (title, summary, why per item id) and may be public.
- `none` — no model is reachable for this run (an API error with no agent, or the agent is offline). Then publish **without summaries**: `summary` is the empty string `""`, the title follows the title rule (untranslated headlines are allowed in this mode, since nothing can translate them), and `why` is the metadata template below. Never fill `summary` with text taken from the source: **no first sentence, no description excerpt, no translation**. When the model comes back, do not rewrite a published issue (§2.7); the next issue is normal.

Rules for `none` mode:
- `why` template, which states the impact on this reader: `<why it reached you>; <evidence>` — e.g. "Release of Ollama, which you follow; 3 publishers", "Matches your interest 'webgpu' and trusted @alice starred it; +412 stars today". Never generic text such as "worth watching".

**`why` rule.** Every item SHOULD have a non-empty `why` that states impact or a judgment, with weighted length ≤ 120 and `sim(why, summary) < 0.5` (§2.3 tokenizer). ACCEPTANCE C6 is the enforced floor (≥ 90% of items).

**Private brief (optional module, OFF by default):** `private_brief: {enabled: false, channel: null}` in the profile. With it off, nothing personal is generated and every private-brief check is N/A.
  - When enabled, write personal implications and the watch list, and deliver them **only** through the user's own private channel (`channel`: `agent-chat`, `email:<address>`, or `im:<SECRET_NAME>` — an IM webhook held in a repo secret).
  - Never store the brief in any repo (public or private), never under `BASE`, never in caches or artifacts that outlive the run.
  - Public text must not depend on it; the forbidden-words gate (§2.6) still runs.

**Copyright rule (hard).** A public item carries only:
- the title per the title rule (social posts: weighted length ≤ 60, never the post text),
- `canonical_url`,
- our **own** `why` (weighted length ≤ 120),
- a `summary` in our own words: context plus significance, **not a translation or paraphrase of the whole source or of any passage of it** (social posts included), `summary ≠ title` (similarity < 0.8), weighted length ≤ 120; or `""` in `none` mode and for headline-only items,
- metadata (dates, tags, signals, sources, via).

A summary MUST NOT share a run of source text at or above the C5b threshold (ACCEPTANCE C5b: 40 characters for Latin-script text, 20 for CJK text), and a summary in another language than its source MUST NOT be a translation of a source passage (ACCEPTANCE C5b, cross-language judgment). Write from the facts, not from the sentences.

**Readable text and script class (one definition; the gate below, ACCEPTANCE C5b and every other check use exactly this).**
- *Decoding* bytes to text, first rule that applies: (1) the `charset` of the HTTP `Content-Type`; (2) an HTML `<meta charset>` or `<meta http-equiv="Content-Type" content="…; charset=…">` in the first 1024 bytes; (3) a byte-order mark (UTF-8, UTF-16LE/BE); (4) charset detection (e.g. `charset-normalizer`); if detection gives nothing, UTF-8 with replacement characters. Never fall back to ISO-8859-1 because HTTP says it is the default. The raw snapshot stores the bytes and the charset used.
- *Readable text:* drop `<script>`, `<style>`, `<noscript>`, `<nav>`, `<header>`, `<footer>`, `<aside>`, `<form>` elements with their contents; drop all remaining tags; decode HTML entities; collapse whitespace to single spaces. Plain text is used as is (entities decoded, whitespace collapsed).
- *Script class* of a text: take its first 6,000 characters, remove URLs (`\S+://\S+`), e-mail addresses and every token that has no letter or is a hex/base64-like run (`[0-9A-Fa-f]{8,}`, `[A-Za-z0-9+/=_-]{24,}` — hashes, IoCs, keys); the text is **CJK** if ≥ 30% of the remaining letters (Unicode categories L*) are in the weight-1 ranges of *weighted length* below (Han, kana, Hangul, fullwidth), else **Latin**. The summary and the source text are each classed by this function; "same script" means equal classes. The gate applies it to the stored source text, the audit to the fetched page — same function, same 6,000-character cut.

**Pre-publish copy gate (MUST, blocking; every item).** Before render, check **every** item with a non-empty summary against the source text it was written from — the stored raw snapshot (page, feed entry, article, post) in `raw/<date>/`:
- same script (script class above): longest common substring of the casefolded, whitespace-collapsed texts **< 40 characters (Latin) / < 20 (CJK)**;
- different script: the separate judge (below) answers the C5b cross-language question for that item, and the answer is "no".
An item that fails is rewritten (or its summary set to `""`) and checked again; an item with a summary but **no stored source text** fails the gate as `no-source` (an item whose facts were not fetched is headline-only, §2.5). Stored text that is empty or near-empty (under 120 weighted characters after dropping URL/header lines) or unrelated to the summary (fewer than a quarter of the summary's distinctive names and numbers appear in it) counts as no stored source; `no-source` blocks unless the summary is `""`. The build does not render or publish until every item passes. ACCEPTANCE C5b's 5-item sample is the post-publish audit, not this gate.

**Separate judge (MUST for judged checks).** The cross-language copy question (the gate above and C5b), C5t and the ACCEPTANCE §J rubric are answered by a **judge context separate from the writer**: a fresh agent or subagent started for judging, given only the questions and their inputs (summary/title, source text, URLs) — never the writer's notes, drafts or rationale. A human is also a separate judge. Record the judge's identity (`kind`: `subagent` / `fresh-agent` / `api-model` / `human`, plus its own id) with each verdict in `state/judgments/<date>.json` (private, §2.9: it quotes source text) and in `build_report.json` (§2.6). A verdict made by the writing context counts as **not judged**.

**Weighted length** `w(s) = Σ_c weight(c)`, weight 1 for characters in U+3000–U+9FFF (CJK punctuation, kana, CJK Ext-A and Unified Ideographs), U+AC00–U+D7AF (Hangul) and U+FF00–U+FFEF (fullwidth forms); weight 120/280 for every other character. So 120 CJK characters or 280 Latin characters reach the cap.

**Truncation.** If `w(summary) > 120`: walk the string, keeping the longest prefix with `w ≤ 119`; remember the last position that ends a sentence (`。！？；!?`, or `.`/`;` followed by a space or the end). If that sentence prefix has `w ≥ 60`, keep it (a trailing `；`/`;` becomes `。`). Otherwise keep the hard prefix, strip trailing `，、,;； ` and append `…`. Apply the same cap to the HTML. (Truncation is a safety net for model output, never a way to make an excerpt.)

**Section-level prose** (`intro`, `note`, `trends[]`) is public text too: `trends[].summary` uses the item rule (`w ≤ 120`); `intro` and `note` are capped at `w ≤ 200`. Same truncation rule.

**Original sources only.** `canonical_url` and `sources[].url` MUST point at the original publisher (vendor, repo, paper, author's own post), never at an aggregator or re-post page. When an item is found through an aggregator, resolve its original link — e.g. schema.org `isBasedOn`, the "source/来源" link, or the aggregator's API — and use that; if none resolves, drop the item. The build fails on any aggregator link.
- **Aggregator seed list** (the single list; ACCEPTANCE C4 uses it; a registry may extend it in `aggregators.json`): `aihot.news`, `techmeme.com`, `news.google.com`, `t.co`, `lnkd.in`, `r.jina.ai`, `news.ycombinator.com`, `hn.algolia.com`, `ainews.com`, `aibase.com`, `readhub.cn`. A host matches when it equals a listed host or ends with `.` + a listed host.
- **Self posts.** A discussion page is the original only when the post has no external link: an HN text post ("Ask HN", or a "Show HN" without a URL) — `https://news.ycombinator.com/item?id=<n>` whose item in `https://hacker-news.firebaseio.com/v0/item/<n>.json` has no `url` field. Only such an HN item URL may be `canonical_url`. For every other HN story, `canonical_url` is the linked article; keep the points in `signals.upvotes` and the discussion link in the scalar `x-discussion` (it is not a source and never appears in `sources`).

Never copy article text, never quote long passages, never republish images or full posts. The reader clicks through to the source.

### 2.6 Render
Render from the store, never by hand. `BASE` = `site.base` (no trailing `/`).

| path under `BASE` | content |
|---|---|
| `<date>/` | HTML: mobile-first, TOC, tags and a `why` line per item, sections folded per `issue.fold_after`, a footer with links to `index.md`, `data.json`, `feed.xml`, `llms.txt`, `SKILL.md` (and 👍/👎, §2.8), and `<link rel="alternate">` for md, json and atom |
| `<date>/index.md` | clean Markdown of the full issue |
| `<date>/data.json` | `digest.v1.3` (§4.3) |
| `latest.md`, `latest.json` | the newest issue |
| `index.json` | the site index, valid against `schema/index.v1.json` (§4.6) |
| `feed.xml` | Atom (rules below) |
| `llms.txt` | what this is; that it updates as soon as each issue is ready (no fixed time); lines `Last-Built: <ISO 8601>` and `Last-Published: <ISO 8601>`; links to every endpoint in this table that is published (`sources.opml` only when `site.publish_sources: true`); how to query by date |
| `SKILL.md` | a tiny skill: "read today's digest" via the URLs above (front matter starts `---\nname:`) |
| `schema/digest.v1.3.json`, `schema/index.v1.json` (and older digest versions you still serve) | **vendored copies** of this skill's schema files, byte-for-byte or with an identical hash (§4.3) |
| `sources.opml` (OPTIONAL, only when `site.publish_sources: true`) | OPML 2.0 (rules below) |
| `build_report.json` (SHOULD) | the JSON output of the latest verification run (ACCEPTANCE, output format): `for_date`, `generated_at`, `schema_version`, `counts`, `results[] {id, layer, level, status}` (judged results add `judge {kind, id}`), including the rubric as result `J` — no secrets, no word list, no source text |

**Atom.** One `<entry>` per issue, newest first. `id` = the issue URL `BASE/<date>/`; `title` = `<site title> <date>`; `updated` = the issue's `published_at` (else `generated_at`); `link rel="alternate"` → `BASE/<date>/`; `summary` = the `top3` titles joined by `；` or `; `, weighted length ≤ 200. No `content` element. The feed's `updated` = the max entry `updated`; "newest entry" means the entry with the max `updated`.

**Source list is opt-in (`site.publish_sources`, default `false`).** Which sources a curator reads, and how they are weighted, is part of that curator's value, so the full subscription list stays private unless the user says otherwise. "Not publishing sources" means: the full source list and its configuration (`sources.yaml`, OPML, per-source weights, lanes, keys, accounts followed for collection) are not published anywhere — no `sources.opml`, no `index.json.sources_opml`, no `llms.txt` link. It does **not** remove attribution: every item always carries its own source links (`url`/`canonical_url`, item `sources[]`, `via`), because attribution is required (§2.5 copyright rule). Any issue-level list of sources (for example an `x-` field or a future top-level `sources[]`) lists only sources actually cited by items of that issue, never the full configured list (ACCEPTANCE B12). `digest.v1.3` has no top-level `sources[]`. Turning `publish_sources` on is a user decision recorded in the interview (§2.1); do not enable it by default or on the agent's own initiative. When it is `false` the build deletes a previously published `sources.opml`.

**OPML** (only when `site.publish_sources: true`). Generate from `sources.yaml`: only sources with `enabled != false` and `opml != false`, and no secret-bearing URL (§2.2). Group by the source's `topic` (`<outline text="<topic>">`; `topic` is one of `profile.topics`). Each child's `text` **starts with the source id** — `<id>` or, for one repo/product of a multi-entry source, `<id>/<repo or product>` — optionally followed by ` — <label>`. Each child has `text` plus:
- feeds: `type="rss"` and `xmlUrl` (GitHub releases → `…/releases.atom`), plus `htmlUrl` when known;
- everything else (pages, changelogs, accounts, JSON APIs): `type="link"` and `htmlUrl` = the human-facing page (for a JSON API, the source's `html` field, e.g. `https://hn.algolia.com/?q=webgpu`). A non-feed source with no human page is left out of the OPML.

**Forbidden-words gate:** run it over every public file (every endpoint above). Its word list is the union of:
- the repo secret `FORBIDDEN_WORDS` (one word per line), exposed to the build as an env var, when `privacy.forbidden_words: secret` (a git-ignored local file MAY mirror it for local runs; CI MUST read the secret, and an unset secret is a failure);
- the **default leak list**, always: absolute local paths (`/home/<user>/`, `/Users/<user>/`, `C:\Users\`), the private-brief channel's address (an email address or webhook URL) when that module is enabled, and the user's own email address(es) known to the pipeline (e.g. the git commit author) unless `site.contact` publishes them on purpose.

Print match counts only, never the words.

**Static-site gotcha:** Jekyll converts any file that starts with `---`, so `SKILL.md` turns into HTML. Fix it in one of two ways:
- add `.nojekyll`, or
- emit `SKILL.md` through a Liquid-only page whose `permalink` is `SKILL.md`.

### 2.7 Publish
There is no template repo; your generated code is the repo.
1. `gh repo create <user>/<name> --public --clone` (or reuse an existing repo the user names; record it as `site.repo`). Write your code, `config/`, `schema/` (vendored, §4.3) and `.github/workflows/daily.yml` into it.
2. Hosting: GitHub Pages (`gh api -X POST repos/<o>/<r>/pages -f build_type=workflow`) or any static host that serves `BASE`.
3. The workflow is named exactly `daily` (`name: daily`, file `.github/workflows/daily.yml`), triggered by `schedule` and `workflow_dispatch`. Cron is in UTC, minute ≠ 0, once a day at any convenient time — there is **no fixed publish time**. **Issue date.** An issue's `date` D is the local date (in `profile.timezone`) at which its run **started**. A run that crosses local midnight keeps D: its `generated_at` and `published_at` may fall on D + 1, and it records its start time (date-time with offset) as `x-run-started-at` on that issue's `index.json` `dates[]` entry (ACCEPTANCE A7, C7). It is never re-dated or rebuilt as the next day's issue. Schedule the run so it normally finishes before local midnight. With `llm.mode: agent`, the agent's own daily task plays this role and dispatches the workflow (or deploys) when its prose is ready. **Declare it** in the public file `state/agent-task.json`:
   ```json
   {"scheduler": "<agent platform, e.g. its routine/automation feature>", "task_id": "<the platform's routine id>",
    "rrule": "FREQ=DAILY;BYHOUR=18;BYMINUTE=17", "timezone": "Asia/Shanghai", "next_run": "2026-10-12T18:17:00+08:00",
    "created_at": "2026-10-11T18:20:00+08:00"}
   ```
   No secrets, no prompt text. `task_id` is the identifier the platform shows for the routine (or `null` if the platform shows none, with `rrule` mandatory). Update `next_run` on every run.
4. **Publish as soon as the build and the pre-deploy checks pass, then record `published_at`.** Two-phase layout:
   1. Job `build`: check out; restore private state (§2.9); collect; build; run the checks that need no live site (schema, C-, D-, E3-checks on the files); save private state; commit only the public ledger/feedback to the default branch; upload the site as the Pages artifact.
   2. Job `deploy` (needs `build`): `actions/deploy-pages` (id `deployment`).
   3. Job `record` (needs `deploy`): read the deploy time from the GitHub Deployments API — `gh api 'repos/<o>/<r>/deployments?environment=github-pages&sha=<GITHUB_SHA>'` → newest deployment → `gh api repos/<o>/<r>/deployments/<id>/statuses` → `created_at` of the first status with `state == "success"` — convert it to `profile.timezone` and write it as `published_at` into that issue's `data.json`, `latest.json`, `index.json`, `feed.xml` and `llms.txt`; run the R-layer checks against the live site; write `build_report.json`; upload a new artifact and deploy again.
   - On a git-push host (Vercel, Netlify, a Jekyll repo), `published_at` = the host's own deploy-complete time when the host exposes it (deploy API or deploy log); only when it exposes none, the commit time of the deploy commit that first carried this content — pushed immediately and confirmed live (the host serves it) before recording. Record which source was used per issue as `x-published-at-source` (`host-deploy` or `commit-time`) on that issue's `index.json` `dates[]` entry. Then commit the `published_at` patch and the report and push again.
   - **Any other host** (a folder served directly, rsync/scp/object storage, no deploy API and no deploy commit): `published_at` = the time the deploy step finished and the new `latest.json` was confirmed served, **written by the deploy step itself** into its own log (`state/deploy-log.jsonl`, one JSON line per deploy: `{date, generated_at, published_at, confirmed_url}`), with `x-published-at-source: deploy-log`.
   - Never estimate `published_at` or backfill it from anything but deploy records (Deployments API, host logs, the deploy step's own log, git history).
5. **Same-day rebuilds.** Rebuilding issue D on day D replaces D everywhere (files, ledger rows of D, §2.3). If the content changed, it gets a new `generated_at` and a new `published_at` after its deploy; if only the rendering changed, both stay. Never rebuild D after the local day D has ended — publish the change as a correction (below) or in the next issue. (Finishing the run that started on D is not a rebuild.)
6. **After an issue is published**, `generated_at` changes only when the content is actually regenerated, and then `published_at` MUST be re-recorded for the new version. Adding or updating `published_at`, `build_report.json`, `corrections[]` or other files, or re-rendering the same content, is **not** a content change and keeps both values. A recorded value that was wrong (e.g. a nominal time instead of the measured one) may be corrected, only to the true value from records (raw file times, run logs, git history), and every such correction MUST be logged publicly in `index.json` → `corrections[]` (§4.6). Never silently rewrite a published timestamp.
7. Secrets live only in repo secrets: `LLM_API_KEY` (optional), `FORBIDDEN_WORDS` (when `privacy.forbidden_words: secret`), `PROFILE_YAML` (if the profile is private), secret-bearing source URLs, private-brief channel credentials (only if that module is enabled), and the built-in `GITHUB_TOKEN`.

**Public allowlist.** The public tree holds only declared public outputs. The site directory holds exactly the §2.6 endpoints (`<date>/` with `index.html`/`index.md`/`data.json`, `latest.*`, `index.json`, `feed.xml`, `llms.txt`, `SKILL.md` (or its Liquid emitter), `sources.opml` (only when `site.publish_sources: true`), `build_report.json`, `schema/*.json`, `.nojekyll`, and the HTML's own static assets if any, listed in `site.public_assets`). A public repo may additionally hold only: source code, `README*`, `LICENSE*`, `.github/`, `.gitignore`, `schema/`, `config/sources.yaml`, `config/profile.yaml` and `state/interview.md` (only with consent, §2.1), `edits/`, `state/publications.json`, `state/feedback.json`, `state/agent-task.json`, `state/corrections.json`, `state/deploy-log.jsonl`. Everything else — in particular candidate files, judgments, fetch logs, snapshots, store — stays out. Declare any extra public path in `site.public_paths` (glob list) so that E4 can check against it. The publish step refuses to commit a path that is not on the allowlist.

If the site is a subfolder of an existing repo, stage **only** that subfolder. Refuse to commit if anything else is staged, or if any path matches §2.9's private patterns.

**Local testing.** The schema's URL pattern requires a dot in the host, so test against `http://127.0.0.1:<port>/…`, not `localhost`. Never publish an issue whose URLs point at a loopback address.

### 2.8 Feedback
- Collect feedback from three places: chat, a feedback issue template, and 👍/👎 links per item. When `site.repo` is not a GitHub repository, point 👍/👎 at `site.feedback_url` (any URL that accepts `?item=<id>&vote=up|down`) or omit them. On GitHub, 👍/👎 are **prefilled GitHub issue links** on `site.repo`: `https://github.com/<site.repo>/issues/new?labels=feedback&title=%F0%9F%91%8D%20<item.id>&body=<urlencoded canonical_url>` (👎 likewise with `%F0%9F%91%8E`).
- Map it to config: interest weights, negatives, trusted people. Per-event and per-source downweights go to `state/feedback.json` (ids and URLs only, no article text):
  ```json
  {"version": 1,
   "items":   {"<item id>": {"up": 0, "down": 1, "canonical_url": "https://…"}},
   "events":  {"<event key>": {"penalty": 0.5}},
   "sources": {"<source id>": {"penalty": 0.5}}}
  ```
- Once a week, send the user a short diff of what changed in `profile.yaml` and `feedback.json`, through `private_brief.channel` when set, else as a GitHub issue on `site.repo` labelled `weekly-diff`.

### 2.9 Privacy and state policy (MUST)
| artifact | contains | where it MAY live |
|---|---|---|
| `raw/<date>/` snapshots | fetched source text | Actions cache/artifacts, or a private repo. **Never in any branch of a public repo.** |
| store (`*.db`) | `raw_json`, titles, text | same as `raw/` |
| editor inputs: candidate files, fact sheets, any file carrying fetched text (`desc`, `page`, `content`, post text); fetch logs | fetched source text | same as `raw/`: keep them under `raw/<date>/` |
| `state/judgments/<date>.json` and pending judge inputs | verdicts with quoted source passages | same as `raw/` (only the judge identity and counts go public, in `build_report.json`) |
| stars snapshots (`stars_total` per repo per day) | numbers | same as `raw/` (or public; they are not text) |
| private brief, watch lists (optional module) | personal context | not generated by default. When enabled: delivered only through the user's private channel; **never stored in any repo**, never under `BASE`, never in caches/artifacts that outlive the run. |
| `state/publications.json` | the publications ledger (§2.3) | public repo OK (no article text) |
| `state/feedback.json` | item ids, event keys, source ids, URLs, weights (§2.8) | public repo OK |
| `state/deploy-log.jsonl` | one line per deploy: `{date, generated_at, published_at, confirmed_url}` (§2.7, any other host) — no text | public repo OK (it is the evidence for `published_at`) |
| `config/profile.yaml`, `state/interview.md` | interests, mutes, trusted people | public **only if the user agreed** (§2.1); otherwise the repo secret `PROFILE_YAML`, or a private config repo |

Beyond these patterns, the public tree is checked against the **allowlist** of §2.7 (ACCEPTANCE E4): any file that is not a declared public output fails. Patterns that MUST NOT exist in **any branch** of a public repo (checked over `git ls-tree -r` of every branch, including `state` and `gh-pages`): a path segment `raw/`, any file `*.db` / `*.sqlite*`; and, when the private brief is enabled, any path segment starting with `private`.

Recommended setup: restore/save `raw/` + store with `actions/cache` (key `store-<date>`, restore-keys `store-`), and also upload them as a short-retention artifact. If the cache is evicted, rebuild dedupe from the public `publications.json`.

## 3. Failure handling
| failure | action |
|---|---|
| a source fails | climb the ladder → skip → ship → record the working method |
| GitHub API limit (60/h unauthenticated) | use `GITHUB_TOKEN` in Actions; cache in private `raw/` |
| no model reachable (`api` error and no agent) | `none` mode for this run (§2.5): titles + metadata `why`, empty summaries; never block publishing |
| a configured section is empty | render `profile.placeholder`; never drop the section |
| the dedupe gate fails | drop the item, or convert it to a follow-up, then rebuild |
| the pre-publish copy gate fails (§2.5) | rewrite that summary from the facts (or set it to `""`), re-check, then render |
| a source is robots-disallowed | disable it (`enabled: false`, `x-disabled: robots`) and tell the user once (§2.2) |
| a forbidden word, a secret-like string or a secret-bearing URL appears in output | fail; remove the text (or move it to the private brief if that module is enabled); rotate any leaked secret |
| an item only has an aggregator URL | resolve the original link; otherwise drop the item |
| 404 right after deploy | wait 60–120 s, then re-check |

### 4.2a Source adapter interface (normative)
Collection is split into one adapter per source type, registered by type name (and, for `social`, by `platform`). The pipeline core never branches on a type; it only calls the adapter. Every adapter, in whatever language you build in, implements the same contract:
- `type` (and `platform` for `social`): the key it is registered under.
- `validate(source) -> errors`: checks the source's own fields (e.g. `accounts` is a non-empty list) at config load.
- `fetch(source, window, state) -> RawItem[]`: fetches using the §2.2 ladder (`method`, `fallbacks`, robots, failure rules) and returns raw items. It never writes to the public tree.
- `RawItem` = `{url, title, published_at, author?, text?, metrics?: {likes?, reposts?, replies?, upvotes?, stars_delta?}, kind}`: `url` is the item's own permalink (the input to `canonical()`, §4.4); `text` stays in private state (§2.9); `metrics` feed the social-proof gate (§2.4).
- `opml(source) -> outline | null`: only for types that have a public feed URL.
Everything after `fetch` (canonical URL, id, dedupe, rank, edit, render) is shared and type-blind. **Adding a platform = adding one adapter** plus its entries in `sources.yaml`; no other file changes. For platforms without a public API (Xiaohongshu, Jike), an adapter may read the user's own exported or bookmarked items, a public profile page within robots/ToS, or a bridge the user runs (e.g. RSSHub, then the source is just `type: feed`); it MUST NOT use the user's session cookies in a public workflow. Items from such platforms are `kind: social`, follow the social-post title rule (§2.5), and link the post's public permalink as `canonical_url`.

### 4.4 Canonical URL and item id (normative)
`canonical(u)` — apply in order:
1. Parse as an absolute URL. The scheme, lowercased, MUST be `http` or `https` (otherwise reject the item). The scheme is **not** part of the result.
2. Host: lowercase, drop a trailing `.`; convert an internationalized host to punycode with **IDNA2008 via UTS #46, non-transitional processing** (so `ß` is kept and encoded, not mapped to `ss`: `straße` → `xn--strae-oqa`; `bücher` → `xn--bcher-kva`). If it starts with `www.`, `m.` or `mobile.` and has ≥ 2 dots, drop that one prefix. Alias `twitter.com` → `x.com`.
3. Port: drop `:80` for http and `:443` for https; keep any other port as `host:port`.
4. Path: empty → `/`; collapse runs of `/` into one; percent-encoding: decode escapes of unreserved characters (`A–Z a–z 0–9 - . _ ~`, e.g. `%7e` → `~`) and uppercase the hex of all other escapes (`%2f` → `%2F`); if the path is not `/`, strip trailing `/`. Otherwise keep the path's case.
5. Fragment: drop.
6. X/Twitter: if host is `x.com` and the path matches `^/([^/]+|i/web)/status(es)?/(\d+)` **case-insensitively**, the result is `x.com/i/status/<digits>` (drop everything else). Other `x.com` paths: lowercase the path and drop the query.
7. Query (all other hosts): split on `&`, percent-decode keys and values (form decoding: `+` becomes a space), drop pairs whose **lowercased key** is in: `utm_source utm_medium utm_campaign utm_term utm_content utm_id utm_name fbclid gclid dclid msclkid igshid mc_cid mc_eid ref ref_src ref_url si spm`. Sort the remaining pairs by (key, value). Re-encode each key and value with RFC 3986 percent-encoding (only `A–Z a–z 0–9 - . _ ~` left unescaped) and join as `k=v` with `&`. Blank values keep the `=`, and a key without `=` (`?flag`) becomes `flag=`.
8. Result: `host + path` + (`?` + query if non-empty).

`id = lowercase hex of SHA-256( UTF-8( canonical(canonical_url) + ("#" + entry if entry) ) )`, first 16 characters.

**`entry`** is used **only** for items taken from a multi-entry page (a changelog / release-notes / "what's new" index page), and then always, even on a day when only one entry is selected, so ids stay stable. Single-item pages (articles, repos, release-tag pages, posts) never use `entry`. Publish the value in the item's `entry` field. Its value comes from the **first** rule that applies:
0. **Not eligible:** an entry headed *Unreleased*, *Upcoming*, *not yet released*, *Next* or Keep-a-Changelog's `[Unreleased]` (in any language) — it is moving content, not a development.
1. **Own page.** If the entry has its own page, link that page as `canonical_url` and use **no** entry. Own page = a URL whose `canonical()` **differs** from the index page's. A `#fragment` permalink is **not** an own page (canonical() drops the fragment); continue with rules 2–5.
2. **GitHub `/releases` listing.** Prefer linking the tag page (rule 1). If you link the listing, entry = the release tag exactly as shown (`v0.40.0`).
3. **Dated entries.** If the page shows a date for each entry, entry = that date `YYYY-MM-DD` as shown by the source, with `-2`, `-3` … in source order for further entries of the same date.
4. **Version-headed, undated entries.** If the page shows no per-entry date but heads each entry with a version label of the page's own product ("Chrome 155-156", "v2.3", "Release 41"), entry = `slug(label)`: lowercase; replace each run of characters outside `[a-z0-9.]` by `-`; trim `-` at both ends; at most 64 characters. "Chrome 155-156" → `chrome-155-156`.
5. **Anchors.** Otherwise use the source's own HTML anchor id of the entry heading if it matches `^[A-Za-z0-9._-]{1,64}$` **and is unique on the page** (one anchor per entry); if there is none, or the same anchor id heads several entries, the entry is not eligible.

Never curator-written text, and never a name taken from inside an entry's body: a model name such as "Sonnet 5.5" mentioned in a dated entry is not a label — that entry's value is its date (rule 3).
- Within one issue, a `canonical(canonical_url)` may repeat only when the items use distinct `entry` values; otherwise the first occurrence wins.
- Across digests, ids are indexes only: on an id match with a different `canonical(canonical_url)`, `canonical_url` wins (treat as different items).

## 5. Registry: digests as each other's sources
A registry is a **separate public repo** (e.g. `ai-digest-registry`), **not part of this skill**. Its value is each curator's **output** — what they collected, reranked and published — not their source list, so entries describe the digest itself. The registry keeps a `registry.json` with its `timezone` (IANA name, default `UTC`), the controlled vocabulary `topics.json` (added by PR; the digest schema has no enum) and `aggregators.json` (extends the seed list of §2.5).

**Joining is optional and off by default.** It is the last step, after the digest is live. The agent forks the registry and opens a PR **only when the user explicitly asks** to join (naming the registry); never silently, never as part of setup, never because a check suggests it.

### 5.1 Entry file `curators/<name>.json`
One small **JSON** file per digest (JSON, not YAML, so no parser can turn a timestamp, `yes` or `null` into another type), valid against `schema/curator-entry.v1.json` (`$id: urn:personal-ai-daily:schema:curator-entry:v1`; a registry contract — digests do not serve it). Times are strings in UTC with `Z` (`"2026-10-11T14:00:00Z"`). Fields:

| field | set by | rule |
|---|---|---|
| `name` | author | required; `^[a-z0-9][a-z0-9-]{1,38}$`; equals the file name without `.json` |
| `url` | author | required; `https://`, ≤ 2048; `canonical(url)` equals `canonical(curator.url)` of the digest's `latest.json`, which in turn equals `canonical(BASE)` (ACCEPTANCE B13) |
| `author` | author | required; the GitHub login, display only (logins can be renamed and re-registered) |
| `author_id` | registry | the **GitHub numeric user id** of the account that opened the admission PR, written at merge and never changed. **Identity is `author_id`**, never the login |
| `people` | author | optional; ≤ 50 public handles, each ≤ 64 (trusted people; ask the user, §2.1) |
| `opml` | author | optional; `https://`, ≤ 2048; allowed only when the digest set `site.publish_sources: true` (its `index.json` has `sources_opml`) |
| `joined_at` | registry | written at merge (= merge time) |
| `delist_history` | registry | list of `{from, to, reason}`, oldest first; `reason` ∈ {`down`, `stale`}; `to` is `null` while the interval is open, and otherwise not earlier than its `from` (checked by G1; JSON Schema cannot compare two fields). The entry is **delisted** iff its last interval has `to: null`. Intervals are never removed |
| `restore` | author | `true` only in a restore PR (§5.3); removed by the registry at merge |
| `x-<name>` | author | optional scalars only (string ≤ 200, number, boolean, null) |

Example (an entry after admission, one delisting and its restore):
```json
{"name": "jane-ai-daily", "url": "https://jane.github.io/ai-daily/", "author": "jane", "author_id": 1234567,
 "joined_at": "2026-10-12T03:00:00Z",
 "delist_history": [{"from": "2026-11-02T01:00:00Z", "to": "2026-11-05T09:30:00Z", "reason": "down"}]}
```

No other field is allowed. Everything else (`topics`, `language`, `schema_version`, `timezone`) is read from the digest's own `index.json`/`latest.json`; its `topics` must come from `topics.json`. A PR that sets or edits `author_id`, `joined_at` or `delist_history` is rejected.
- **Names are unique and never reused.** A PR whose `name` (or whose `canonical(url)`) already exists — listed or delisted — is rejected; first merged wins. A PR that deletes a whole entry file is always rejected (history and name reservation stay; leaving is a delisting).
- **Changes to an existing entry** (rename, `url` move, `people`, restore) are accepted only from a PR whose opener's numeric id equals `author_id`. A new account means a new entry.

### 5.2 Admission (PR) — the same conditions as the daily recheck
Registry CI checks, and blocks the merge on, exactly these (ACCEPTANCE §R, G1–G3):
1. **Entry:** the file validates against `curator-entry.v1.json`; `name` = file name; for a new entry the name/url are not taken, and for an existing entry the PR opener's numeric id = `author_id`; `canonical(url)` = `canonical(curator.url)` = `canonical(BASE)`; the digest is not a fixture (`generated_from: fixture`).
2. **Liveness (now):** `latest.json`, `index.json` and the Atom feed answer 200 and validate with the registry's **own vendored** schemas selected by `schema_version` (§4.3) — ACCEPTANCE B3 (issue schema), B4, B5 (incl. index schema), B6.
3. **Freshness (now):** the newest `index.json.dates[].published_at` is at most **14 days** before the CI run time (compared as instants, UTC).

The rest of the ACCEPTANCE R layer also runs and is posted on the PR (and in the registry's status page) as a **report, not a gate**. Past cadence (A7/A7b), a missing `sources.opml` (B9/B9s are N/A without a published source list) or any other historical result never blocks admission; only the three conditions above, evaluated at the time of the check, decide.

### 5.3 Daily recheck, delisting and restore
Registry CI re-runs conditions 2 and 3 once per registry day:
- **down** = condition 2 failed on **3 consecutive completed checks** of that digest. A day on which the registry CI did not run, or the run is void (the registry's own reachability probe failed), neither counts nor resets the streak.
- **stale** = condition 3 fails.
- **Delisting** appends `{from: <check time>, to: null, reason}` to `delist_history`; the **file is kept** (history, name reservation). Delisted digests are skipped by `type: registry` subscriptions and by the leaderboard (§5.5). Rename and `url` moves are not accepted while delisted (restore first).
- **Restore:** once the digest is live and fresh again, the author (opener id = `author_id`) opens a PR that only adds `"restore": true`; CI runs §5.2. At merge the registry sets the open interval's `to` to the merge time and removes `restore`. The history stays; `name`, `author_id` and `joined_at` are kept.

### 5.4 Using peers as sources
- **Curator identity** is `canonical(curator.url)`. `via`, echo-loop checks (D4) and self-link checks (C4) all compare that value, never `name`.
- **Subscribe.** A `type: registry` source picks listed (not delisted) curators by `topics` and/or `curators` (a list of names) and/or `people` overlap. It pulls their `latest.json`.
- **Dedupe across digests.** Key on `canonical(canonical_url)` (§4.4); `id` is an index. A peer item about something you already have only adds to `signals.source_count` (one publisher per peer, §2.3) and appends the peer to `sources`.
- **Echo-loop guard and hop limit.** `via` is nearest first (§4.3). When you consume a peer item, put the peer `{name, url, item_url}` **first**, followed by the peer's own `via`. Drop the item if any `canonical(via[].url)` equals your own `canonical(curator.url)`, or if `via` would exceed **2 hops — aggregator hops count**. Example: a peer found an item on AIHOT (`via: [AIHOT]`); you take it from the peer → `via: [peer, AIHOT]` (2 hops, allowed); a third digest taking it from you would need 3 hops and drops it (it can still pick the item up directly or from AIHOT).
- **Lane and trust.** Registry items enter the `discover` lane unless the curator is in your trusted list. They must pass the social-proof gate like any other item. Always credit the peer in `via`.

### 5.5 Co-selected leaderboard (experimental, non-normative)
A registry MAY publish a board of items that several members picked, keyed by item identity `k = canonical(canonical_url)` (§4.4; the item `id` is its index). **This section is not part of the contract**: no check depends on it, and two registries may count differently. Detailed counting and anti-gaming rules will be set from real data once the registry has members. Any implementation keeps three principles:
1. **One vote per author.** All entries with the same `author_id` count as one voter for an item, however many digests or issues picked it.
2. **Re-shares don't vote.** A pick whose `via` contains a member digest **anywhere** (some `canonical(via[].url)` equals a member's `canonical(curator.url)`, listed or delisted) is a re-share and gives no vote. Hop order does not matter.
3. **Pick time = the time the registry first fetched that issue** (from its own fetch log), never a curator-written `published_at` and never the item's source date. A registry that runs a board keeps a log of when it first saw each member issue.

### 5.6 Source packs (opt-in only)
The registry merges the `sources.opml` of **members who opted in** (`site.publish_sources: true`, `opml` in their entry) into per-topic **verified source packs**. A source counts as verified once ≥ 3 opted-in curators use it. Curators who did not opt in are never inferred from their item links. A new digest can bootstrap its `sources.yaml` from the packs for its topics.

## 6. Design trade-offs
- **Static output plus a single-file store:** free hosting, trivially agent-readable, replayable.
- **Rules for trust, a model for prose:** dedupe, ranking and gates are deterministic because they are the trust layer; the model (the user's agent or an API) writes the prose. Without a model the digest still ships, but without summaries — never with copied text.
- **Events, not URLs, are the unit:** readers hate repeats more than they love coverage.
- **Two lanes plus a social-proof gate:** without them a personal feed becomes an echo chamber or noise.
- **Public/private split enforced by gates,** not by discipline: raw text and personal context never touch a public branch.
- **Only the ledger is public state:** dedupe survives cache loss, and nothing copyrighted or personal is exposed.
- **Shared ids from one exact canonical-URL algorithm** let a network of digests dedupe without coordinating.
- **Schemas pinned by `$id` + hash, hosted by everyone:** no curator's domain is a dependency of anyone else's digest.

## 7. Acceptance
`ACCEPTANCE.md` lists every criterion, split into the R layer (public, blocking) and the S layer (self-attested), plus a judgment rubric. Turn them into your own verification, written in the stack you chose; it lives in the user's repo, not in this skill.

Run it after each publish and fix every failure. Publish its JSON output as `build_report.json`. Report "provisionally done" after the first run and "done" after two scheduled runs, per the Done definition, and give the user the URLs at that point. Re-run it daily as part of the workflow, and open an issue in the repo for any failure you cannot fix automatically.

## Appendix A. Mapping an existing digest (e.g. Horizon) to digest.v1.3
Generators that were not built from this skill can still publish `digest.v1.3`. Watch for:
- **Dates:** many tools use the UTC date. `date` MUST be the local date in the curator's timezone; a run between 00:00 and 08:00 in UTC+8 otherwise lands on the previous day. Make the zone configurable.
- **No full-content export:** never map `content`, `selftext`, `description` or other body text into the JSON (the schema rejects `content`/`body`/…), and never use a description excerpt as `summary`. Map only the title (title rule, §2.5), own summary (model-written, ≤ the §2.5 cap; its language matches `language`) and own `why` (e.g. an "impact" block; else the §2.5 metadata template).
- **ids:** native ids such as `{source}:{subtype}:{native_id}` are not `id`. Recompute `id` per §4.4 from the URL and keep the native id as `x-<tool>-id`.
- **sources:** must mean *provenance*: `[{url: canonical_url}]` plus other publishers that reported the same event. Web-search references gathered during enrichment are not provenance: leave them out (or publish only their count as `x-reference-count`; `x-*` values are scalars).
- **canonical_url:** the linked article. A discussion page (HN, Reddit) is the original only for a text post with no external link (§2.5); otherwise put the discussion link in `x-discussion` and the points in `signals.upvotes`.
- **Missing concepts:** no publications ledger → `first_seen_at = date` and no `follow`/`key` until a ledger exists; `via: []`; topics must be mapped onto the registry's `topics.json`; `language` should carry a region where meaningful (`zh-CN`); a 0–10 score goes to `x-score`; `signals.source_count` per §2.3 (≥ 1).
